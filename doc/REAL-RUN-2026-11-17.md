# 实机调试报告：bsend × 本机 qBittorrent 5.3.0（2026-11-17）

范围：`rust/coverage` 分支的 Rust 铺种引擎，对本机真实下载器（41,885 条种子）与
真实 PT 站点（配置里 9 个启用的 NexusPHP 站）实测。本文只记事实与结论，改动细节见
`rust/README.md` 与提交记录。

## 一、环境

| 项 | 值 |
| --- | --- |
| 下载器 | qBittorrent **5.3.0**，`http://127.0.0.1:9091`，41,885 条种子（41,882 已完成、3 条未完成） |
| 配置 | `%LOCALAPPDATA%/BoxSend/boxsend.json`（源站 147，启用 9，全部 NexusPHP） |
| Cookie | 同目录 `cookies.json`，9 个 host |
| 站点 | luckpt / hdsky / chdbits / hdhome / cmct / audiences / ttg / pter / hhanclub |
| 平台 | Windows 11，bsend release 单文件 6.1 MB |

## 二、规模与性能实测

| 指标 | 实测值 |
| --- | --- |
| 首扫（41,882 次 `/torrents/files`，并发 6） | **214 s**，进程峰值 **233 MB** |
| 去重结果 | 41,882 条种子 → **3,385 段内容**（12.4×） |
| `coverage.json` | 15 MB（明文 JSON，原子写） |
| 增量重扫（零文件清单请求） | **14 s** |
| 覆盖基线 `prime`（9 站，零站点请求） | 13.8 s，**3,938 格**判为「已在做种」 |

去重比之所以这么高：同一段文件在多个站各有一条种子（不同 info hash、逐文件清单全等），
索引按 manifest 摘要并成一段内容——这正是铺种方案的前提，实机验证成立。

## 三、实机暴露并修复的问题

按严重程度排列。每条都是「实机可见的现象 → 根因 → 修法 → 回归手段」。

### P0-1 连不上下载器：`/app/version` 不再是 JSON

- 现象：`bsend scan` 直接失败「GET /api/v2/app/version 回包不是 JSON」。
- 根因：qB **5.x 起该端点回纯文本**（`v5.3.0`），4.x 才是 `{"version": ...}`。
- 修法：`test_connection` 两版都认（纯文本直接用，`{` 开头才按 JSON 解析）。
- 回归：e2e `e2e_single_tracker_field_and_plain_version`（mock 回纯文本）。

### P0-2 每个请求慢 30 秒：系统代理残留

- 现象：单次 `scan` 启动耗时 31 s；设 `NO_PROXY=*` 后 0.04 s。
- 根因：注册表里 `ProxyServer=socks=127.0.0.1:9090` 虽 `ProxyEnable=0`，reqwest 仍会读它，
  每次请求先去连不存在的 SOCKS 直到超时。
- 修法：qB 客户端与站点客户端统一 `.no_proxy()`（PT 站 passkey 与 IP 绑定，本不该走代理）。
- 回归：实机计时；无网络环境依赖，不进单测。

### P0-3 「已在做种」预筛完全失效：qB 5.x 不返回 `tracker_hosts`

- 现象：`prime` 之前所有格子都当未覆盖；实机 3,385 段内容 × 9 站全部要检索。
- 根因：qB 5.3 的 `/torrents/info` 只有 `tracker`（当前那条 announce），没有代码里读的
  `tracker_hosts`（4.6+）或 `trackers`（更老）。
- 修法：解析层三级兜底 `tracker_hosts → trackers(|) → tracker`，并过滤 `** [DHT] **` 一类占位符；
  顺带修 `infohash_v2: ""` 空串污染身份表。
- 回归：`qbittorrent::tests` 四条（5.x 单字段 / 数组 / 管道串 / 伪 tracker）+ e2e 预筛走通。

### P0-4 `/torrents/files` 参数名：每次都先白撞一发 400

- 现象：首扫 41,882 条 × 2 次请求（`hashes=` 回 400 → 回退 `hash=` 才有数据）；偶发一次失败
  就把该内容判 `failed` 7 天。
- 根因：qB 5.3 该端点只认 `hash`；实现是「先 hashes 再 hash」，且失败不重试。
- 修法：成功的参数名记在 `files_param` 里复用；失败重试一次（间隔 300 ms）。
- 回归：e2e mock 对两个参数名都回数据；实机首扫从「约 8 万次请求」降到 4.2 万次。

### P0-5 预算与节奏按 `search()` 记账，实际一次检索要发 3–7 发请求

- 现象：一轮 4 格「站内没有」花掉 28 单位检索预算；一次 `search()` 在 1 秒内连发 5 条查询词。
- 根因：查询词阶梯（全名 → 去组标签 → 词元 → 截短 → 宽松 4 条）每级都是一发 HTTP，
  而预算与站间隔只加在 `search()` 外层。PT 站会把这种连发当爬虫。
- 修法：`search()` 增加 `gate: &mut dyn FnMut() -> bool`，**每个真实请求前领号**
  （预算 -1 + 按站间隔睡）；`SiteClient` 与编排层同步改造，区分
  `Hit / Miss / BudgetExhausted`（后者不落负缓存）。
- 回归：e2e 预算用例改为按请求记账（预算 1 发 → 两个站都「没排上」，不写格子）；
  resolver 单测覆盖 `BudgetExhausted` 停止整轮走查。

### P1-1 站点限流页（HTTP 200）被当成「站内没有」

- 现象：hdsky 回 200，正文却是 `<title>403</title>` +「请求过于频繁，限制访问间隔 60 秒/次」；
  旧逻辑解析不出详情锚 → 记 Miss → 整站 7/30 天不再问。
- 修法：`block_notice(html)` 识别限流/封禁页并转成错误；`error_is_rate_limited` 认它；
  该站本轮最低间隔抬到 60 s（`rateLimitFloorSec`），且支持 `siteIntervals` 逐站预设（hdsky: 65）。
- 回归：单测 `block_pages_are_detected`；e2e `e2e_block_page_is_failed_not_miss`；
  实机复测：hdsky 首格即 `failed`（note 含「限流」），不再污染负缓存。

### P1-2 cookie 失效的另一种形态：`index.php?returnto=…`

- 现象：pter 的所有请求 302 到 `index.php?returnto=torrents.php…`，页面是首页；旧检测只认
  `login/signin/enter.php`，于是被当「站内没有」。
- 修法：登录墙提示串补 `returnto=`。
- 回归：e2e `e2e_returnto_redirect_is_login_wall`；实机复测 pter 两格直接 `failed`
  （note「被跳到登录页（cookie 可能已失效）」），单格只花 1 发请求。

### P1-3 站点 announce 域名 ≠ 页面域名

- 现象：`prime` 基线里 luckpt 一格都没有；实际有 557 条种子挂 `tracker.luckpt.de`，
  而页面是 `pt.luckpt.de`。chdbits 同理（`chdbits.xyz`，136 条）。
- 影响：693 条种子被误判为「未覆盖」——对 hdsky 这种 60 秒/次的站，代价极高。
- 修法：`SiteConf.announce_hosts`（页面 host + 内置别名 + `overrides.announceHosts`），
  预筛与源站优先排序都用 `matches_tracker`。
- 回归：config 单测（别名加载与子域边界）、sites 单测（别名表不许删）；
  实机基线从 3,244 格升到 3,938 格。

### P2-1 刚检索过的目标站又被当源站问一遍

- 修法：转种臂的源站名单剔除当前目标站；参与站只有一家时直接 `waitSource`。
- 效果：单格「站内没有」从 7+3 发降到 7 发（实机 plan 的 source 预算从 10 降到 0）。

### P2-2 首扫优先级等于随机

- 根因：优先级次要键是 `first_seen`，首扫全部相同 → 实际按 contentKey 字典序挑。
- 修法：记 `added_on`（qB），优先级用「成员种子最晚入库时间」；老索引缺该字段按 0 处理。

### P2-3 队列规模失控

- 根因：3,385 内容 × 9 站 = 30,465 个待办对象（各带名字 / 全部 hash / tracker 表）。
- 修法：每站每轮最多排 `roundBudget` 格（预算撑不起更多）；`--limit` 语义不变。

### P2-4 预算耗尽被算进「预筛跳过」

- 修法：`RoundReport.skipped_no_budget` 独立计数；`preskipped` 只表示零请求的预筛跳过。

`bsend prime` 后 `bsend report`（9 个启用站、零站点请求）：

读法：格子 = 已有结论的「内容 × 站」；「未判定」= 这段内容在该站还没查过。
基线里的 100% 是「查过的都已在做种」，不是「全部内容都已覆盖」——
真正的缺口是每站 2,400–3,300 格待判定，需要按轮次消耗预算逐步查。

## 五、真实请求成本（决定轮次节奏）

| 场景 | 请求数 / 格 | 说明 |
| --- | --- | --- |
| 已在做种（预筛） | 0 | 基线覆盖了 3,938 格 |
| 站内没有（miss） | **7** | 严格 3 条查询词 + 宽松 4 条；20 格实测 138 发（6.9/格） |
| 站内命中 A/B | 4–6 | 命中即停 + 详情页 + 种子下载 |
| cookie 失效 / 限流 | 1 | 立刻报错，不浪费后续查询 |

按默认 8 s 间隔、每站 200 预算：单站一轮约 27 分钟、跑完 25–60 格；4 站并发。
hdsky 需 65 s 间隔（`siteIntervals`），同样预算下单轮约 12 格。

## 七、操作提示

- **pter 的 cookie 已失效**（跳 `index.php?returnto=…`），需在 GUI 里重新登录/刷新 cookie；
  在此之前跑 pter 只会得到 `failed`，不会误记负缓存。
- **hdsky 限流严格**：请在 `boxsend.json` 的 `assist.siteIntervals` 里设 `{"hdsky": 65}`，
  否则第一轮会先撞一次墙（撞了也会自动退避到 60 s，但白费一发）。
- 建议 cron / 计划任务每 30–60 分钟跑一轮 `bsend run`，`prime` 只在索引大改后跑一次。
