# 实机调试报告：bsend × 本机 qBittorrent 5.3.0（2026-11-17）

范围：`rust/coverage` 分支的 Rust 辅种引擎，对本机真实下载器（41,885 条种子）与
真实 PT 站点（配置里 9 个启用的 NexusPHP 站）实测。本文只记事实与结论，改动细节见
`rust/README.md` 与提交记录。

## 二、规模与性能实测

| 指标 | 实测值 |
| --- | --- |
| 首扫（41,882 次 `/torrents/files`，并发 6） | **214 s**，进程峰值 **233 MB** |
| 去重结果 | 41,882 条种子 → **3,385 段内容**（12.4×） |
| `coverage.json` | 15 MB（明文 JSON，原子写） |
| 增量重扫（零文件清单请求） | **14 s** |
| 覆盖基线 `prime`（9 站，零站点请求） | 13.8 s，**3,938 格**判为「已在做种」 |

去重比之所以这么高：同一段文件在多个站各有一条种子（不同 info hash、逐文件清单全等），
索引按 manifest 摘要并成一段内容——这正是辅种方案的前提，实机验证成立。

## 三、实机暴露并修复的问题

按严重程度排列。每条都是「实机可见的现象 → 根因 → 修法 → 回归手段」。

### P0-1 连不上下载器：`/app/version` 不再是 JSON

- 现象：`bsend scan` 直接失败「GET /api/v2/app/version 回包不是 JSON」。
- 根因：qB **5.x 起该端点回纯文本**（`v5.3.0`），4.x 才是 `{"version": ...}`。
- 修法：`test_connection` 两版都认（纯文本直接用，`{` 开头才按 JSON 解析）。
- 回归：e2e `e2e_single_tracker_field_and_plain_version`（mock 回纯文本）。

### P0-2 每个请求慢 30 秒：系统代理残留

- 现象：单次 `scan` 启动耗时 31 s；设 `NO_PROXY=*` 后 0.04 s。
- 根因：注册表里 `ProxyServer=socks=127.0.0.1:9090` 虽 `ProxyEnable=0`，reqwest 仍会读它，
  每次请求先去连不存在的 SOCKS 直到超时。
- 修法：qB 客户端与站点客户端统一 `.no_proxy()`（PT 站 passkey 与 IP 绑定，本不该走代理）。
- 回归：实机计时；无网络环境依赖，不进单测。

### P0-3 「已在做种」预筛完全失效：qB 5.x 不返回 `tracker_hosts`

- 现象：`prime` 之前所有格子都当未覆盖；实机 3,385 段内容 × 9 站全部要检索。
- 根因：qB 5.3 的 `/torrents/info` 只有 `tracker`（当前那条 announce），没有代码里读的
  `tracker_hosts`（4.6+）或 `trackers`（更老）。
- 修法：解析层三级兜底 `tracker_hosts → trackers(|) → tracker`，并过滤 `** [DHT] **` 一类占位符；
  顺带修 `infohash_v2: ""` 空串污染身份表。
- 回归：`qbittorrent::tests` 四条（5.x 单字段 / 数组 / 管道串 / 伪 tracker）+ e2e 预筛走通。

### P0-4 `/torrents/files` 参数名：每次都先白撞一发 400

- 现象：首扫 41,882 条 × 2 次请求（`hashes=` 回 400 → 回退 `hash=` 才有数据）；偶发一次失败
  就把该内容判 `failed` 7 天。
- 根因：qB 5.3 该端点只认 `hash`；实现是「先 hashes 再 hash」，且失败不重试。
- 修法：成功的参数名记在 `files_param` 里复用；失败重试一次（间隔 300 ms）。
- 回归：e2e mock 对两个参数名都回数据；实机首扫从「约 8 万次请求」降到 4.2 万次。

### P0-5 预算与节奏按 `search()` 记账，实际一次检索要发 3–7 发请求

- 现象：一轮 4 格「站内没有」花掉 28 单位检索预算；一次 `search()` 在 1 秒内连发 5 条查询词。
- 根因：查询词阶梯（全名 → 去组标签 → 词元 → 截短 → 宽松 4 条）每级都是一发 HTTP，
  而预算与站间隔只加在 `search()` 外层。PT 站会把这种连发当爬虫。
- 修法：`search()` 增加 `gate: &mut dyn FnMut() -> bool`，**每个真实请求前领号**
  （预算 -1 + 按站间隔睡）；`SiteClient` 与编排层同步改造，区分
  `Hit / Miss / BudgetExhausted`（后者不落负缓存）。
- 回归：e2e 预算用例改为按请求记账（预算 1 发 → 两个站都「没排上」，不写格子）；
  resolver 单测覆盖 `BudgetExhausted` 停止整轮走查。

### P1-1 站点限流页（HTTP 200）被当成「站内没有」

- 现象：hdsky 回 200，正文却是 `<title>403</title>` +「请求过于频繁，限制访问间隔 60 秒/次」；
  旧逻辑解析不出详情锚 → 记 Miss → 整站 7/30 天不再问。
- 修法：`block_notice(html)` 识别限流/封禁页并转成错误；`error_is_rate_limited` 认它；
  该站本轮最低间隔抬到 60 s（`rateLimitFloorSec`），且支持 `siteIntervals` 逐站预设（hdsky: 65）。
- 回归：单测 `block_pages_are_detected`；e2e `e2e_block_page_is_failed_not_miss`；
  实机复测：hdsky 首格即 `failed`（note 含「限流」），不再污染负缓存。

### P1-2 cookie 失效的另一种形态：`index.php?returnto=…`

- 现象：pter 的所有请求 302 到 `index.php?returnto=torrents.php…`，页面是首页；旧检测只认
  `login/signin/enter.php`，于是被当「站内没有」。
- 修法：登录墙提示串补 `returnto=`。
- 回归：e2e `e2e_returnto_redirect_is_login_wall`；实机复测 pter 两格直接 `failed`
  （note「被跳到登录页（cookie 可能已失效）」），单格只花 1 发请求。

### P1-3 站点 announce 域名 ≠ 页面域名

- 现象：`prime` 基线里 luckpt 一格都没有；实际有 557 条种子挂 `tracker.luckpt.de`，
  而页面是 `pt.luckpt.de`。chdbits 同理（`chdbits.xyz`，136 条）。
- 影响：693 条种子被误判为「未覆盖」——对 hdsky 这种 60 秒/次的站，代价极高。
- 修法：`SiteConf.announce_hosts`（页面 host + 内置别名 + `overrides.announceHosts`），
  预筛与源站优先排序都用 `matches_tracker`。
- 回归：config 单测（别名加载与子域边界）、sites 单测（别名表不许删）；
  实机基线从 3,244 格升到 3,938 格。

### P2-1 刚检索过的目标站又被当源站问一遍

- 修法：转种臂的源站名单剔除当前目标站；参与站只有一家时直接 `waitSource`。
- 效果：单格「站内没有」从 7+3 发降到 7 发（实机 plan 的 source 预算从 10 降到 0）。

### P2-2 首扫优先级等于随机

- 根因：优先级次要键是 `first_seen`，首扫全部相同 → 实际按 contentKey 字典序挑。
- 修法：记 `added_on`（qB），优先级用「成员种子最晚入库时间」；老索引缺该字段按 0 处理。

### P2-3 队列规模失控

- 根因：3,385 内容 × 9 站 = 30,465 个待办对象（各带名字 / 全部 hash / tracker 表）。
- 修法：每站每轮最多排 `roundBudget` 格（预算撑不起更多）；`--limit` 语义不变。

### P2-4 预算耗尽被算进「预筛跳过」

- 修法：`RoundReport.skipped_no_budget` 独立计数；`preskipped` 只表示零请求的预筛跳过。

## 九、真实辅种全流程（绝世天劫 → hdhome）

选样：`[绝世天劫].Armageddon.1998.BluRay.1080p.AVC.DTS-HD.MA5.1-CMCT`（43.42 GB、327 文件、
71 条本地种子、已在 8 个参与站做种，唯独 hdhome 没有）；hdhome 站内确实有该版本
（`Armageddon 1998 BluRay 1080p AVC DTS-HD MA5.1-CMCT`，标题写法不同）。

第一跑失败在「校验后只到 0%」。逐层排查结论：

1. **分片结构没问题**：hdhome 的 .torrent 与本地 51 条备份成员中 50 条的 pieces 完全一致
   （8 MiB × 5177 片，piece hash 流全同）——跨种本该成立；
2. **路径没问题**：qB 报 `content_path = J:\Download\[绝世天劫]...`，与磁盘一致；
3. **真凶是三个连锁的 qB 5.x 行为差异**：
   - `torrents/resume|pause` 在 qB 5.0+ 已删（404），改名 `torrents/start|stop`——
     我们的启停从未生效（校验完不作种、回滚的「保持暂停」也是空话）；
   - **停止态的种子不会开始校验**（`paused=true` 添加后状态 `stoppedDL` 永远 0%），
     必须 `start` 一次才进入 `checkingDL`；`recheck` 对停止态无效；
   - `is_checking` 少了 5.x 的 `checkingDL/checkingUP/queuedForChecking/metaDL`，
     「排队校验中」被当成「校验不过」提前回滚。

修复：启停端点新名优先、404 回退旧名；add 三套参数（`stopped`/`started`/`paused`）都发；
推送尾巴改成「停止态添加（dlLimit=1 兜底）→ start 触发校验 → 100% 解除限速」；
`is_checking` 补齐 5.x 状态名。新增 e2e `e2e_qb5_start_stop_endpoints` 钉住两端形态。

修复后复跑：`checkingDL` 稳步推进（12% @ 75s，dl_limit=1、dlspeed=0）→ 43 GB 核对约 8 分钟
→ 100% 自动做种。结论：**清单全等（B 级）+ 布局一致即可辅种成功**，
但整条链路必须按 qB 5.x 的语义走，否则会被 0% 假象误判成「文件对不上」。

## 十、转种流程（伪装者 → luckpt）

选样：`The.Disguiser.Complete.HDTV.1080p.AAC.x264-JING`（伪装者全集 HDTV，已在 8 个参与站做种，
唯独 luckpt 没有）。目标站 luckpt 确实没有该种子（站内检索未命中）——正好走转种臂。

```
[luckpt] 转种草稿（站内没有；源种定位成功（hdsky：info hash 一致（c6b5f7fbbbd5…）），
         转种草稿待人工确认） → https://hdsky.me/details.php?id=27637
转种草稿（1 条，v1 不自动上传，人工确认后走 GUI 版转种）：
  「The.Disguiser.Complete.HDTV.1080p.AAC.x264-JING」源种 hdsky → 目标 luckpt
```

55 秒走完全程：luckpt 检索未命中（7 发）→ 源种定位（tracker 优先回已在做种的 hdsky，
3 发命中、**A 级 info hash 一致**）→ 出草稿（`reseed_draft` + `source` 记录落盘）。
v1 的转种只到草稿为止（上传涉及 148 站表单适配，属后续阶段）；草稿里已有
源站详情页链接、判定级别、目标站，人工确认后可走 GUI 版转种上传。

### 已知局限：站点列表标题 ≠ 种子 info.name

另一例（`About.Kim.Sohee.2022.MULTi.COMPLETE.FR.BLURAY-Psaro`）在转种源站定位时 8 个源站
51 发请求全部落空。排查发现：该内容在 chdbits 的列表标题是
`Da-eum So-hee 2022 1080p Blu-ray AVC DTS-HD MA 5.1-Psaro`（同一影片、同一上传者 Psaro，
标题被站方本地化改写），而种子的 info.name 是英文标题。名称匹配连不上两种标题
（词元重叠不足），检索臂拿不到候选，清单级判定（A/B）根本没机会跑。

这是名称检索的固有盲区：**判定靠清单，但候选挑选靠名字**。可能的改进方向：
① 候选挑选放宽到「年份 + 上传者/组名」等弱特征，下载候选 .torrent 后由清单判定兜底
（代价是请求变多）；② 优先用目标站/源站自己的历史发布名（需要保存成员种子名）。
本轮记录为已知局限，未改启发式——判定口径动之前需要更多样本。

## 十二、转种全流程 Rust 原生化（不再交接 GUI 版）

背景：伪装者转种发到 luckpt 被 LuckAudit 自动审核打回（81 分，2 错 1 警）：
① 检测到中文字幕但未选中字标签 ② 简介缺 IMDb/豆瓣/TMDB 链接 ③ MediaInfo 为空。
暴露的问题是转种链路缺「发布信息体检」，且上传能力只在 Swift GUI 版里。

本轮改动：

1. **新增 `bsend::reseed`**（约 700 行）：源站详情页解析（标题/副标题/简介/MediaInfo/

## 十三、审阅模式 + 发后自检 + 解析防坑 + 开站 95 个（2026-11-18）

背景：用户三问——① 上传是直发 HTTP 还是无头浏览器？② 如何避免再出现缺信息/不准确？
有没有审阅模式？③ 开启更多有 cookie 的站点。全部落地：

1. **上传通道**：直发 HTTP（reqwest blocking + multipart/form-data + Cookie 头），
   不是无头浏览器。审阅模式复用同一条字段构造链路，只是不 POST。
2. **审阅模式（review_reseed）**：源页解析 → 预检 → 构造上传字段但不提交，
   字段清单（长值截断）+ 预检结论全量输出。CLI `bsend reseed --draft N`（默认审阅）
   与 GUI「审阅」按钮（字段清单进任务日志）；`--yes` / 「确认转种」才真发。
   抽出 `prepare_upload` / `prepare_released` 与正式转种共用，两路字段永不漂移。
3. **发后自检（verify_posted）**：上传成功后回读新种详情页，核对标题 / MediaInfo /
   IMDb·豆瓣·TMDB 落没落上，漏了日志点名（只警告不推翻结论）。
4. **实机审阅立刻抓出 4 个问题并修掉**（伪装者草稿 hdsky → luckpt）：
   ① 标题混入 `[50%]` 促销角标 → `strip_promo_suffix`（保留 `[中字]` 内容标签）；
   ② 简介兜底把整页 58KB HTML 当 descr 提交 → 容器解析补单引号 `id='kdescr'`
   （hdsky 实际就是单引号，双引号匹配不到才误入兜底）；兜底改「简介」表行 → 正文纯文本；
   ③ 「中字」标签勾上了仍误报警告 → 判定改为「wanted 一个都没匹配上才警告」
   （复选框 value 是数字编码，拿 value 含不含关键词判必误报）；
   ④ MediaInfo 为空 → 正确阻断（源页确实没有，与上次 LuckAudit 被拒同因，这次拦在发前）。
5. **开站**：审计 boxsend.json × cookies.json（按条目 domain 后缀匹配 + expirationDate
   时效），95 个 NexusPHP 站有有效 cookie 但未启用 → 备份 `boxsend.json.bak-20261118-075010`
   后批量翻 `enabled=true`。参与站 9 → 104；5 个无/过期 cookie 站（byr/tlf/yinghua/
   azusa/generationfree）保持关闭；17 个非 NexusPHP（Blu/Gazelle/Unit3D/XBTIT/TNode/
   custom 等）有 cookie 但 Rust v1 检索只支持 NexusPHP，暂不开。
   `bsend report` 验证 104 站全出现（新站各 3,385 格未判定）。

验证：reseed 单测 15 个全过（新增 promo/引号/兜底/审阅渲染/发后自检 7 个）；

## 十四、站点官方预审接入（LuckAudit pre-audit，2026-11-18）

背景：「lucky站点官方有发种前的预审核功能，使用该功能辅助」。luckpt 上传页带
LuckAudit 面板（`js/luckaudit.js`），发布前可先送官方评分。接入转种流水线：

1. **协议**（逆自 luckaudit.js `collectTorrentInfo`）：`POST /api/auto-audit/pre-audit`，
   请求体与上传字段同构（name/small_descr/description/technical_info/type/quality/
   tags/external_links/user_info = 页内 `LUCK_AUDIT_USER` 嵌入 JSON），响应
   `{passed,status,totalScore,errorCount,…,details:[{ruleType,message,level,score,
   suggestion}],suggestions}`。检测 = 上传页 HTML 含 "luckaudit"。
2. **传输**：JSON POST 被站点 Cloudflare 拦（应用侧只认 JSON 时又会 502 炸源站），
   表单编码 + PHP 嵌套语法（`type[id]=404`、`quality[medium][id]=7`）畅通且
   `$request->input()` 能解析 → `json_to_form` 摊平 JSON 为括号表单对。
3. **WAF 归因（实机矩阵）**：Rust 客户端一直 403「网站防火墙」而 Python/PowerShell
   同请求 200。逐项二分推翻了 TLS 指纹假说（rustls/native-tls/curl 全 403，
   Python OpenSSL 同正文同样 403）：**触发项是表单体里内联 `on*=` 事件属性的
   出现次数**——2 处放行、4 处即拦，8 张去掉 onload/onclick 的 `<img>` 放行。
   NexusPHP 简介截图段天然带一串 onload/onclick，纯体积（18K 填充）无碍。
   修复：`strip_event_handlers` 只在预审载荷里剥标签内事件属性（正文 "on=…" 等
   字样不动、多字节 UTF-8 原样），真实上传 multipart 一字不动。
4. **接入点**：审阅（review_reseed）输出「官方预审」段（总分/❌⚠️🔍 计数 + 明细
   + 官方建议原文）；`run_reseed` 上传前 `passed=false` 直接 bail（站点自动审核
   一样会拒，先拦省白传）；接口异常降级为提示不拦。
5. **实机验证**（伪装者草稿 hdsky → luckpt）：官方预审 200，未通过（总分 49/100，
   ❌ 6）——未选择分类/媒介/编码/音频/分辨率 + MediaInfo 为空，全部如实列出。
   这正是「辅助」价值：官方口径比本地三查更细（多出分类/媒介/编码/音频/分辨率
   五项）。
6. **遗留**：build_upload_fields 只填标题/副标题/简介/MediaInfo/条目链接/标签，
   分类与质量下拉（type / X_sel）未做映射、留表单默认 0——官方预审会一直报
   「未选择」。下一步候选：按表单选项文案从种子名推断（HDTV/1080p/x264/AAC 一类）
   自动选档，选对了官方预审才可能满分通过。

验证：workspace 105 测试全过（新增 strip_event_handlers 单测）+ fmt + clippy
零告警，CI 彩排通过；reseed --draft 1 实机审阅输出官方预审段。
